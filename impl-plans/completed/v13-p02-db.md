## Intent and Context

Add every v1.3 column and table in ONE new Alembic revision, so that the wave-2 plans can
write repositories against fixed models. Enum-like columns are strings. This plan does not
import `telescreen.core.vocabulary` values that p01 adds in parallel; string defaults are
literals.

Imitate:

- `db/models/issues.py:IssueRow` and `db/models/notifications.py:NotificationTemplateRow`
  (`Base, kw_only=True`, `Mapped[...] = mapped_column(...)`, unannotated `__tablename__`);
- `db/migrations/versions/0003_v1_2.py` (an idempotent upgrade that inspects
  tables, columns and indexes, then backfills; a downgrade that drops what exists);
- `tests/db/test_v12_migration.py` (fresh schema plus an upgrade from the previous
  revision with a round trip).

## Non-goals

- No repositories or services; the feature plans own those.
- Never edit `0001_initial.py`, `0002_v1_1.py` or `0003_v1_2.py`.

## Invariants

- `0004_v1_3` has `down_revision = "0003_v1_2"` and is idempotent: running upgrade twice
  is a no-op.
- `0001_initial` builds tables from the current ORM metadata, so a fresh database already
  has the v1.3 schema. `0004` therefore creates only the tables, columns and indexes that
  are missing.
- New `issues` columns are nullable or have a server default, so existing rows stay
  valid.
- Every model file stays under 1000 lines. New issue tables go into a new file.

## Deliverables

1. `db/models/issues.py`, `IssueRow` new columns:
   - `priority: String(16)`, not null, `server_default="medium"`, `default="medium"`;
   - `priority_manual: Boolean`, default false, `server_default="0"`;
   - `needs_review: Boolean`, default false, `server_default="0"`;
   - `merged_into_id: String(36) | None`, indexed;
   - nullable `archive_kind: String(32)`, `archive_until`, `archive_threshold: Integer`,
     `archive_baseline: Integer` and `archived_at` (timezone-aware DateTime).

   Add `Index("ix_issues_status_merged", "status", "merged_into_id")` through
   `__table_args__`, merged with any existing args.
2. New `db/models/issues_v13.py`. Columns are those of design 13.1, with these types:
   - `SavedViewRow` (`saved_views`): name String(64), query Text, sort String(16), period
     String(64) nullable, visibility String(16), owner_member_id String(36) indexed,
     position Integer, created_at, updated_at.
   - `SavedViewStarRow` (`saved_view_stars`): PK (view_id, member_id).
   - `SavedViewDefaultRow` (`saved_view_defaults`): PK member_id; view_id.
   - `IssueCommentRow` (`issue_comments`): issue_id indexed, author_ref String(256), body
     Text, created_at, edited_at nullable, deleted_at nullable.
   - `IssueMentionRow` (`issue_mentions`): PK (comment_id, member_id); created_at.
   - `IssueSubscriptionRow` (`issue_subscriptions`): PK (issue_id, member_id); subscribed
     Boolean, reason String(16), updated_at.
   - `IssueBookmarkRow` (`issue_bookmarks`): PK (issue_id, member_id); created_at.
   - `ExternalIssueLinkRow` (`external_issue_links`): issue_id indexed, kind String(16), url
     String(2048), title String(200), external_ref String(256) nullable, created_by
     String(256), created_at. `UniqueConstraint("issue_id", "url")`.
   - `IssueMergeRow` (`issue_merges`): primary_issue_id indexed, merged_issue_id indexed,
     merged_by, merged_at, unmerged_by nullable, unmerged_at nullable.
   - `OwnershipRuleRow` (`ownership_rules`): position Integer, source String(32) nullable,
     pattern String(512), team_id String(36), enabled Boolean, created_by, created_at,
     updated_at.
3. New `db/models/alerts.py`:
   - `AlertRuleRow` (`alert_rules`): name String(64) unique, enabled, trigger_kind
     String(32), threshold Integer nullable, window_minutes Integer nullable, filters_json
     Text, actions_json Text, action_interval_minutes Integer, muted_until nullable,
     last_fired_at nullable, created_by, created_at, updated_at.
   - `AlertFireRow` (`alert_fires`): rule_id, issue_id, trigger_kind String(32), outcome
     String(32), notification_count Integer, run_id nullable, error_code String(32)
     nullable, fired_at. `Index("ix_alert_fires_rule_issue_at", "rule_id", "issue_id",
     "fired_at")`.
4. `db/models/notifications.py`:
   - `NotificationRow.category: String(32) | None`;
   - new `NotificationSettingRow` (`notification_settings`): PK (member_id, category);
     channel String(16), updated_at.
5. New `db/models/integrations.py`: `IntegrationCheckRow` (`integration_checks`): PK kind
   String(32); checked_at, ok Boolean, error_code String(32) nullable.
6. `db/models/__init__.py`: export every new row class.
7. `db/migrations/versions/0004_v1_3.py`:
   - create the 14 missing tables and the missing columns and indexes;
   - backfill `issues.priority` with
     `UPDATE issues SET priority = CASE WHEN severity IN ('critical','high') THEN 'high'
     ELSE 'medium' END`;
   - backfill `issues.needs_review = true` WHERE `status IN ('unresolved','regressed')`.
   The backfills run only when the `priority` column was added in this run (track a flag),
   so the upgrade stays idempotent. The downgrade drops the v1.3 tables, indexes and
   columns that exist.

## Tests

- `tests/db/test_models.py`: `EXPECTED_TABLES` gains the 14 names and the count goes from
  34 to 48. The minimal-row test still inserts one row per table, so supply minimal values
  for the new tables in the same style.
- `tests/db/test_v13_migration.py`:
  - fresh schema at head -> the 14 tables and the new `issues` and `notifications`
    columns exist; a second `upgrade head` is a no-op;
  - a `0003_v1_2` schema with 3 issues (critical/unresolved, medium/regressed,
    high/resolved), then upgrade -> priorities high, medium and high; needs_review true,
    true and false;
  - downgrade to `0003_v1_2` -> the new tables are gone and the issue rows are intact;
  - a v13 row of each new model round-trips through the ORM on SQLite.
