## Intent and Context

Add the v1.2 table and columns as ORM fields and as one idempotent Alembic revision.
`0001_initial` builds tables from the current ORM metadata, so on a fresh database it
already creates the v1.2 columns. `0003_v1_2` must therefore inspect the live schema and
add only what is missing, as `0002_v1_1` does.

Imitate:

- `src/telescreen/db/migrations/versions/0002_v1_1.py` (`NEW_TABLES`, `NEW_COLUMNS`,
  `NEW_INDEX_TABLES`, the clone-and-create pattern, idempotent upgrade and downgrade);
- `src/telescreen/db/models/directory.py:MemberRow` (field style, `kw_only=True`);
- `tests/db/test_v11_migration.py` (migration test structure).

## Non-goals

- Never edit `0001_initial.py` or `0002_v1_1.py`.
- No repositories or services; feature plans own them.
- No DB enum or check constraints: statuses stay `String(32)`.

## Invariants

- Every new ORM field has a default (`default=None`, or `default="manual"` plus
  `server_default="manual"`), so existing constructors such as
  `NotificationService.send:NotificationRow(...)` and
  `DirectoryService.create_member:MemberRow(...)` compile unchanged.
- `down_revision = "0002_v1_1"`, `revision = "0003_v1_2"`.
- The role backfill never grants more than the member's tokens already allowed.

## Deliverables

1. **`db/models/notifications.py`**:
   - `NotificationRow` appends, all nullable with `default=None`: `event_kind`
     `String(32)`, `template_name` `String(64)`, `template_version` `Integer`, `set_name`
     `String(64)`, `target_index` `Integer`, `error_code` `String(32)`.
   - New `NotificationTemplateRow` (`__tablename__ = "notification_templates"`):
     - columns `id` `String(36)` PK, `name` `String(64)`, `version` `Integer`,
       `event_kind` `String(32)`, `description` `String(200)` nullable, `subject` `Text`,
       `body` `Text`, `email_subject` / `email_body` / `slack_body` `Text` nullable,
       `active` `Boolean`, `created_by` `String(80)`, `created_at` `DateTime(tz)`;
     - `UniqueConstraint("name", "version")` and `Index("ix_notification_templates_name_active",
       "name", "active")`.
2. **`db/models/directory.py`**:
   - `MemberRow` appends `role: str | None` (`String(16)`, default None) and
     `last_sign_in_at: datetime | None` (default None), plus
     `Index("ix_members_role_active", "role", "active")` in `__table_args__`;
   - `TeamMembershipRow` appends `origin: str` (`String(16)`, `default="manual"`,
     `server_default="manual"`).
3. **`db/models/__init__.py`**: export `NotificationTemplateRow` in imports and `__all__`.
4. **`0003_v1_2.py`**:
   - `NEW_TABLES = ("notification_templates",)`.
   - `NEW_COLUMNS`: `notifications` (6 columns), `members` (`role`,
     `last_sign_in_at`), `team_memberships` (`origin`).
   - Indexes are created when missing.
   - Backfill, only when `members.role` was added in this run (the same "added" flag
     pattern as `base_severity_added` in 0002): read
     `api_tokens(member_id, scopes)` where `revoked_at IS NULL AND member_id IS NOT
     NULL`, compute the highest scope per member (`admin` -> `admin`, else `write` ->
     `responder`, else `read` -> `viewer`; `ingest`-only -> no role), and run `UPDATE
     members SET role = :role WHERE id = :id`. Use bound parameters through
     `sa.text`; never format values into SQL.
   - `downgrade()` drops the added columns and table when present. Use
     `op.batch_alter_table` for SQLite column drops, as 0002 does.

## Pitfalls

- A NOT NULL `origin` column added to an existing `team_memberships` table needs
  `server_default="manual"` in the `op.add_column`, or the add fails on rows that
  already exist.
- When cloning columns from metadata for `op.add_column`, copy the column
  (`column.copy()` or `Column(...)`, as 0002 does). Do not reuse the bound Column object.
- A fresh database (0001 already created everything) must run 0003 as a no-op with no
  error, and must not backfill twice.

## Tests (`tests/db/test_v12_migration.py`)

- Fresh SQLite database upgraded to head -> `notification_templates` exists; the
  `notifications`, `members` and `team_memberships` columns exist.
- A database at `0002_v1_1` made to look like v1.1 (drop the v1.2 columns and table, as
  `test_v11_migration.py` simulates older schemas):
  - members A (bound active admin token), B (write and read tokens), C (read token
    revoked), D (ingest-only), E (no token);
  - upgrade -> roles A `admin`, B `responder`, C null, D null, E null;
  - `team_memberships.origin` == `manual` for existing rows.
- Upgrade twice (head -> head) is a no-op. Downgrade to `0002_v1_1` removes the
  additions, and upgrade again restores them.
- ORM round trip: insert a `NotificationTemplateRow` and a `NotificationRow` with the new
  fields, read them back, and check that a duplicate (name, version) raises
  `IntegrityError`.
- Integration (marked `integration`, PostgreSQL via `TELESCREEN_TEST_DATABASE_URL`): the
  same backfill scenario. It is skipped offline by design.
